# Планирование: анализ, идентификация проблем и поиск решений

## Существующие и потенциальные проблемные места

1. **Неочевидный и ненадежный путь заказа из онлайн-магазина в MES.**

   На C4-диаграмме нет явной связи `Shop API -> MES API` или `Shop API -> Messages Queue`. При этом по бизнес-процессу после оформления заказ должен попасть в MES для расчета стоимости. Если передача заказа реализована неявно через CRM, общую БД, ручные действия или периодические выборки, заказ может долго не попадать в обработку.

2. **MES API выполняет слишком много задач.**

   MES API одновременно обслуживает интерфейс операторов, показывает список заказов, назначает заказы операторам, рассчитывает стоимость изделий, принимает запросы от внешних API-пользователей и взаимодействует с хранилищем 3D-файлов. Это смешивает быстрые пользовательские операции и тяжелые вычислительные операции в одном компоненте.

3. **Расчет стоимости не выделен в отдельный компонент.**

   Расчет находится внутри MES API. Из-за этого нельзя независимо масштабировать вычисления, управлять нагрузкой расчета отдельно от операторского интерфейса и изолировать деградацию. Один сложный файл может надолго занять ресурсы MES и ухудшить работу остальных сценариев.

4. **Внешние API-пользователи подключены напрямую к MES API.**

   После открытия API нагрузка от партнеров пришла в тот же компонент, которым пользуются операторы. У системы нет отдельного внешнего входа для B2B-заказов и отдельного контура обработки партнерского трафика. Рост или всплеск активности партнеров напрямую влияет на производственный контур.

5. **Единственный инстанс каждого приложения является точкой отказа и ограничением масштабирования.**

   Онлайн-магазин, CRM и MES работают по одному инстансу. Любой сбой или перегрузка инстанса приводит к деградации соответствующего бизнес-процесса. Для MES это особенно критично, потому что через него проходят расчет стоимости, работа операторов и B2B API.

6. **Базы данных работают в одном инстансе на чтение и запись.**

   `Shop DB` и `MES DB` обслуживают и чтение, и запись в одном экземпляре. Медленные чтения для списков, дашбордов и внутренних выборок могут конкурировать с транзакционными изменениями заказов. При росте числа заказов эта проблема будет усиливаться.

7. **CRM API связан с Shop DB, что похоже на нарушение границ владения данными.**

   На диаграмме `CRM API` обращается к `Shop DB`. Если CRM напрямую читает или пишет данные онлайн-магазина, возникает сильная связность между сервисами: изменение схемы БД магазина может ломать CRM, а ответственность за данные заказа становится размытой.

8. **Статусы заказа распределены между системами без явного владельца процесса.**

   Статусы меняются в онлайн-магазине, MES и CRM. Нет выделенного владельца жизненного цикла заказа, который отвечает за допустимые переходы, восстановление после ошибок и согласованность состояния между системами. Из-за этого заказ может зависнуть между этапами процесса.

9. **Ручное подтверждение производства через CRM может стать бизнес-бутылочным горлышком.**

   Подтверждение производства выполняется в CRM. Для стандартных заказов после успешного расчета цены ручное участие продавца может быть избыточным. Если подтверждение требуется всегда, рост заказов напрямую увеличивает очередь ожидания продавцов и задерживает старт производства.

10. **Нет сквозной наблюдаемости процесса заказа.**

    Сейчас проблемы разбираются по жалобам клиентов, партнеров и операторов. Команда не видит единую картину прохождения заказа через онлайн-магазин, CRM, MES, очередь сообщений и расчет стоимости. Из-за этого сложно быстро понять, где заказ остановился и что нужно исправлять.

11. **Релизный процесс замедляет исправление инцидентов.**

    Dev деплоится автоматически, но release и prod деплоятся вручную. E2E-проверки выполняются вручную одним QA-инженером. При серьезных дефектах релизы задерживаются, а в условиях роста нагрузки это мешает быстро выпускать исправления для проблемных сценариев.

12. **Хранилище 3D-файлов является критичной зависимостью для отказоустойчивости расчета.**

    Shop API загружает 3D-файлы, а MES использует их для расчета стоимости. Если файл недоступен, поврежден, не прошел проверку или ссылка на него потеряна, заказ не сможет пройти расчет. Значит, устойчивость хранения и корректность работы с файлами напрямую влияют на прохождение заказа.

## Инициативы для устранения нежелательных ситуаций

1. **Определить или создать сервис, ответственный за жизненный цикл заказа, и наладить надежный обмен между системами.**

   Нужен явный владелец процесса, который будет управлять переходами заказа между этапами и координировать взаимодействие онлайн-магазина, CRM и MES. Это может быть отдельный `Order Workflow`-сервис. Передача заказа и изменений его состояния должна быть явной, контролируемой и восстанавливаемой после ошибок.

2. **Выделить расчет стоимости в отдельный сервис.**

   Расчет стоимости нужно вынести из MES API в отдельный компонент. Такой сервис сможет обрабатывать вычислительно тяжелые задачи независимо от операторского интерфейса и масштабироваться отдельно от MES.

3. **Разделить внешний B2B API и внутренний MES API.**

   Для партнерских интеграций нужен отдельный входной контур. MES API должен оставаться внутренним сервисом производственного процесса, а внешний поток заказов не должен напрямую конкурировать с работой операторов.

4. **Применить CQRS для MES и оптимизировать read-часть.**

   Команды изменения состояния заказа и чтение списков/дашбордов стоит разделить. Для операторского интерфейса можно построить отдельную модель чтения, оптимизированную под быстрый показ актуальных заказов и статусов, а производственные команды оставить в транзакционном контуре MES.

5. **Повысить отказоустойчивость критичных компонентов.**

   Нужно убрать зависимость от единственного инстанса для ключевых приложений и проработать устойчивость баз данных и хранилища 3D-файлов. Особое внимание нужно уделить компонентам, без которых заказ не может перейти к расчету или производству.

6. **Убрать прямое владение чужими данными и стабилизировать контракты между системами.**

   CRM не должна зависеть от внутренней схемы `Shop DB`. Взаимодействие между системами должно идти через API или события, а для данных заказа нужно определить зоны ответственности: что принадлежит Shop, что принадлежит CRM, а что принадлежит MES.

7. **Автоматизировать типовые подтверждения производства.**

   Для стандартных заказов, которые не требуют ручной проверки, можно сократить участие продавца и переводить заказ дальше автоматически. Продавцам стоит оставлять исключения: нестандартные заказы, ошибки входных данных или ситуации, где действительно нужно бизнес-решение.

8. **Добавить проверку 3D-файлов до постановки в расчет.**

    Файл нужно проверять до запуска тяжелого расчета: доступность в хранилище, базовая корректность, поддерживаемый формат и пригодность для дальнейшей обработки. Это уменьшит число заказов, которые зависают из-за проблем с исходными данными.

9. **Ввести базовую наблюдаемость прохождения заказа.**

    На первом этапе достаточно обеспечить возможность быстро найти заказ и увидеть его путь между системами. Детальный набор метрик, логов и трассировки должен быть проработан отдельно в следующих заданиях.

## Приоритизация инициатив

Приоритизация строится от бизнес-ущерба, риска и измеримости результата. Первым шагом нужно ввести базовую наблюдаемость прохождения заказа: без мониторинга команда не сможет надежно понять, где именно заказы зависают. После этого нужно остановить зависание заказов и разгрузить MES, потому что именно эти проблемы напрямую приводят к просрочкам и потере контрактов. Затем нужно повышать устойчивость, чистить границы между системами и ускорять релизы.

## Целевая архитектура через полгода

Через полгода целевая архитектура должна быть эволюцией текущей системы, а не полной заменой всех приложений.

1. **Заказ проходит через явный управляемый workflow.**

   У процесса заказа есть владелец. Онлайн-магазин, CRM и MES взаимодействуют через явные контракты, а переходы между этапами контролируются и восстанавливаются при сбоях.

2. **Расчет стоимости вынесен из MES API.**

   Отдельный сервис расчета получает задачи на обработку, работает с 3D-файлами и возвращает результат в основной процесс заказа. MES API больше не смешивает операторские операции с тяжелыми вычислениями.

3. **B2B-интеграции отделены от производственного API.**

   Партнеры работают через отдельный внешний контур. Внутренний MES API обслуживает производственные сценарии и не принимает внешний трафик напрямую.

4. **MES использует разделение command/read-сценариев.**

   Производственные команды проходят через транзакционный контур MES, а чтение списков и дашбордов выполняется через оптимизированную модель чтения.

5. **Критичные компоненты устойчивы к одиночным сбоям.**

   Ключевые приложения масштабируются горизонтально, а базы данных и хранилище 3D-файлов имеют понятную стратегию восстановления. Сбой одного экземпляра не должен останавливать прохождение заказов.

6. **Границы данных между системами стали явными.**

   CRM, Shop и MES взаимодействуют через API или события, а не через прямую зависимость от чужих таблиц. Это снижает риск поломок при изменении схемы данных.

7. **Команда видит путь заказа между системами.**

   Поддержка и разработка могут найти заказ и понять, на каком этапе он находится. Детальные решения по мониторингу, логированию и трейсингу описываются в следующих архитектурных документах.

## Три инициативы на ближайшие полгода

1. **Ввести базовую наблюдаемость прохождения заказа.**

   Это первый шаг, потому что без мониторинга команда будет оценивать проблемы и эффект изменений по жалобам клиентов, а не по фактам.

2. **Определить или создать владельца жизненного цикла заказа и наладить надежный обмен между системами.**

   Главный бизнес-ущерб сейчас связан с тем, что заказы зависают и клиенты не получают изделия в обещанный срок. Поэтому сначала нужно сделать путь заказа явным и управляемым: от оформления до расчета, подтверждения и передачи в производство.

3. **Выделить расчет стоимости в отдельный сервис.**

   Расчет стоимости длительный и непредсказуемый по времени. Пока он находится внутри MES API, он мешает операторским сценариям и плохо масштабируется. Выделение сервиса расчета разгрузит MES и даст основу для роста B2C и B2B-направлений.
