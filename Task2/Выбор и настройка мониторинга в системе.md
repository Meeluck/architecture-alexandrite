# Выбор и настройка мониторинга в системе

## Мотивация

Мониторинг позволит компании перейти от реактивной поддержки к управлению системой по фактам. Сейчас жалоба клиента является первым сигналом проблемы, а должна быть последним: команда должна видеть деградацию раньше, чем заказ нарушит обещанный срок.

Для бизнеса мониторинг даст:

- снижение числа просроченных заказов за счет раннего обнаружения зависаний;
- более быструю диагностику жалоб клиентов и партнеров;
- понимание, хватает ли текущей инфраструктуры при росте заказов;
- возможность обосновывать технические инициативы цифрами, а не предположениями;
- контроль качества B2B API после подключения партнеров.

Для инженерной команды мониторинг даст:

- видимость состояния Shop API, CRM API, MES API, RabbitMQ, баз данных и S3-хранилища;
- возможность быстро отличать проблему приложения от проблемы инфраструктуры;
- данные для проверки эффекта от архитектурных изменений.

## Выбор подхода к мониторингу

1. **RED для API и сервисов.**

   RED отслеживает rate, errors и duration. Этот подход подходит для `Shop API`, `CRM API`, `MES API` и будущего сервиса расчета стоимости, потому что эти компоненты обслуживают запросы пользователей, операторов, продавцов и партнеров.

2. **USE для инфраструктуры.**

   USE отслеживает utilization, saturation и errors. Этот подход подходит для виртуальных машин, PostgreSQL, RabbitMQ и S3-хранилища, потому что здесь важно понимать загрузку ресурсов, насыщение и ошибки на уровне инфраструктуры.

3. **Четыре золотых сигнала для общей картины надежности.**

   На уровне всей системы полезно смотреть latency, traffic, errors и saturation. Это позволит собрать единый обзор здоровья системы: сколько трафика приходит, где растут задержки, где появляются ошибки и какие компоненты близки к перегрузке.

## План действий

1. **Выбрать стек мониторинга.**

   Для метрик можно использовать Prometheus, Grafana и Alertmanager.

2. **Подключить сбор инфраструктурных метрик.**

   Нужно собирать показатели виртуальных машин, баз данных PostgreSQL, RabbitMQ и S3-хранилища. Это даст базовую видимость состояния ресурсов.

3. **Инструментировать Shop API, CRM API и MES API.**

   В Java-сервисах можно использовать Micrometer, в C#-сервисе - стандартные .NET metrics/OpenTelemetry. Нужно добавить метрики запросов, ошибок, времени ответа и бизнес-событий заказа.

4. **Настроить мониторинг RabbitMQ.**

   Нужно собирать состояние очередей, количество сообщений в обработке, проблемные сообщения и состояние потребителей.

5. **Собрать бизнес-дашборд по заказам.**

   На одном экране должны быть видны поток заказов, распределение по статусам, возраст заказов в статусах и отдельный разрез B2C/B2B. 

6. **Собрать технические дашборды по компонентам.**

   Отдельные дашборды нужны для Shop API, CRM API, MES API, RabbitMQ, Shop DB, MES DB и S3. На них должны быть видны трафик, ошибки, задержки, ресурсы и насыщенность.

7. **Настроить первичные алерты.**

   Алерты должны срабатывать на зависание заказов, рост очередей, рост ошибок API, деградацию MES, проблемы доступа к 3D-файлам и приближение БД к лимитам.
